# Seguridad SIGA — cambios de base de datos para la DBA

Este documento describe los cambios de schema necesarios para que el backend arranque con
`ddl-auto: validate`.

## Alcance: sólo `usuario`, `rol` y una tabla nueva `refresh_token`

El resto del schema actual **no se toca**. En particular, hay tablas que hoy tienen
foreign keys hacia `usuario(id_usuario)` pero que **este backend no usa ni mapea aun** (no hay
ninguna entidad JPA sobre ellas hoy): `notificacion`, `historial_asignacion`, `solicitud_cambio`,
`evento_unico` (la de solicitud/aprobación, distinta de `evento_unico_academico` que sí se usa),
y las columnas `id_usuario_creador`/`id_usuario_aprobador` de `asignacion_aula` (la tabla se usa,
esas dos columnas puntuales no). Se dejan intactas — cambiarlas sería alcance de otro trabajo, no
de esta fase. Por eso es clave que **`usuario.id_usuario` mantenga su tipo actual (`int8`)**: es
lo único que garantiza que esas FKs no mapeadas sigan siendo válidas sin tocarlas.

**Antes de correr nada de esto en un ambiente compartido, por favor validar a mano cómo van a
quedar esas relaciones no mapeadas** (los `id_usuario_creador`/`id_usuario_aprobador` de
`asignacion_aula`, y las FKs de `notificacion`/`historial_asignacion`/`solicitud_cambio`/
`evento_unico` hacia `usuario`) — nosotros no tenemos entidades para inspeccionar ese lado hoy,
así que si hay datos reales cargados ahí conviene que lo revisen ustedes antes del `ALTER`, no
después.

## Qué cambia conceptualmente

**Hoy**: `usuario` tiene `id_usuario, id_rol, nombre, apellido, email, activo,
eliminado`, con FK a una tabla `rol(id_rol, nombre)` normalizada. No hay tabla de sesiones ni
passwords — no es utilizable para login, es sólo la forma que tenía reservada.

**Pasa a ser**:
- `usuario`: pierde `nombre`, `apellido`, `id_rol` (no hay "nombre para mostrar" separado del
  email en este diseño, y el rol deja de ser una tabla normalizada). Gana `password_hash`
  (BCrypt). `email` se renombra a `correo` (es el identificador de login). `activo` se renombra
  a `habilitado`. `eliminado` se mantiene igual.
- `rol` (tabla) **se elimina**. El rol pasa a ser un enum Java de dos valores fijos
  (`SUBSECRETARIA`, `AUXILIAR_AULICO`) persistido como texto en una tabla de colección nueva
  `usuario_rol` (un usuario puede tener más de un rol).
- `refresh_token` (tabla nueva): sesiones de refresh, no existía nada parecido antes.

## DDL propuesto

⚠️ **`ADD COLUMN password_hash ... NOT NULL` va a fallar si `usuario` ya tiene filas** (no hay
default razonable para un hash de password). Confirmado con el equipo que la tabla no está en
uso todavía — si en su ambiente tiene filas de prueba viejas, la forma más simple es vaciarla
antes (`TRUNCATE TABLE usuario CASCADE;`, revisando antes que no haya datos que les importe
conservar en las tablas que dependen de ella por FK). Si prefieren no truncar, avísennos y
ajustamos el DDL para agregar la columna nullable + backfill en vez de `NOT NULL` directo.

```sql
-- 1) Sacar la relación usuario -> rol vieja y las columnas que ya no se usan.
--    DROP COLUMN de id_rol se lleva puesta la FK (fk_usuario_rol) y el índice
--    (idx_usuario_rol) que dependen de esa columna; no hace falta dropearlos aparte.
ALTER TABLE usuario DROP COLUMN id_rol;
ALTER TABLE usuario DROP COLUMN nombre;
ALTER TABLE usuario DROP COLUMN apellido;

-- 2) La tabla rol normalizada ya no tiene nada que la referencie: se puede eliminar.
DROP TABLE rol;

-- 3) Renombrar columnas para que coincidan con el mapeo JPA actual.
ALTER TABLE usuario RENAME COLUMN email TO correo;
ALTER TABLE usuario RENAME CONSTRAINT usuario_email_key TO usuario_correo_key;
ALTER TABLE usuario RENAME COLUMN activo TO habilitado;

-- 4) Password hash (BCrypt, ~60 caracteres reales; se deja margen).
--    Ver advertencia arriba si la tabla ya tiene filas.
ALTER TABLE usuario ADD COLUMN password_hash varchar(255) NOT NULL;

-- 5) id_usuario hoy es un int8 "manual" (sin secuencia/identity asociada). El backend
--    inserta usuarios sin pasar el id explícitamente, así que necesita autogenerarlo.
ALTER TABLE usuario ALTER COLUMN id_usuario ADD GENERATED BY DEFAULT AS IDENTITY;

-- 6) Roles como tabla de colección (reemplaza a la tabla `rol` + FK usuario.id_rol).
CREATE TABLE usuario_rol (
    id_usuario int8 NOT NULL,
    rol varchar(30) NOT NULL,
    CONSTRAINT fk_usuario_rol_usuario FOREIGN KEY (id_usuario) REFERENCES usuario(id_usuario),
    CONSTRAINT chk_usuario_rol_valor CHECK (rol IN ('ADMIN', 'AUXILIAR_AULICO')),
    CONSTRAINT uq_usuario_rol UNIQUE (id_usuario, rol)
);
CREATE INDEX idx_usuario_rol_usuario ON usuario_rol USING btree (id_usuario);

-- 7) Refresh tokens (tabla nueva, sesiones de login).
CREATE TABLE refresh_token (
    id_refresh_token bigserial NOT NULL,
    id_usuario int8 NOT NULL,
    token_hash varchar(255) NOT NULL,
    revocado bool NOT NULL DEFAULT false,
    fecha_revocacion timestamp NULL,
    reemplazado_por int8 NULL,
    motivo_revocacion varchar(20) NULL,
    fecha_expiracion timestamp NOT NULL,
    fecha_creacion timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT refresh_token_pkey PRIMARY KEY (id_refresh_token),
    CONSTRAINT uq_refresh_token_hash UNIQUE (token_hash),
    CONSTRAINT fk_refresh_token_usuario FOREIGN KEY (id_usuario) REFERENCES usuario(id_usuario),
    CONSTRAINT fk_refresh_token_reemplazado_por FOREIGN KEY (reemplazado_por) REFERENCES refresh_token(id_refresh_token),
    CONSTRAINT chk_refresh_token_motivo CHECK (motivo_revocacion IS NULL OR motivo_revocacion IN ('ROTATION', 'LOGOUT', 'CASCADE'))
);
CREATE INDEX idx_refresh_token_usuario ON refresh_token USING btree (id_usuario);
```

**`chk_usuario_rol_valor` y `chk_refresh_token_motivo` son extra, no los pide el mapeo JPA**
(el enum se valida del lado de la aplicación) — los sugerimos porque es una tabla que ustedes
también pueden llegar a tocar a mano, y un `CHECK` evita que se cuele un valor con typo
directamente por SQL. Si prefieren no tenerlos por simplicidad, se pueden omitir sin romper nada
del lado del backend.

## Validación

El backend arranca con `ddl-auto: validate` — si el schema no coincide exactamente con el mapeo JPA, 
la aplicación ni siquiera inicia. Si aplican el DDL tal como está arriba, el backend arranca correctamente.

## Referencia: mapeo completo `usuario`

| Columna | Tipo | Null | Notas |
|---|---|---|---|
| `id_usuario` | `int8` (identity) | NOT NULL | PK, ya existía; se le agrega autogeneración |
| `correo` | `varchar(150)` | NOT NULL, unique | antes `email` — identificador de login |
| `password_hash` | `varchar(255)` | NOT NULL | nueva, BCrypt |
| `habilitado` | `bool` | NOT NULL, default `true` | antes `activo` |
| `eliminado` | `bool` | NOT NULL, default `false` | sin cambios |

## Referencia: `usuario_rol`

| Columna | Tipo | Null | Notas |
|---|---|---|---|
| `id_usuario` | `int8` | NOT NULL | FK a `usuario` |
| `rol` | `varchar(30)` | NOT NULL | `'ADMIN'` o `'AUXILIAR_AULICO'`, texto plano (no hay tabla `rol` normalizada) |

## Referencia: `refresh_token`

| Columna | Tipo | Null | Notas |
|---|---|---|---|
| `id_refresh_token` | `bigserial` | NOT NULL | PK |
| `id_usuario` | `int8` | NOT NULL | FK a `usuario` |
| `token_hash` | `varchar(255)` | NOT NULL, unique | SHA-256 del token real, nunca el token crudo |
| `revocado` | `bool` | NOT NULL, default `false` | |
| `fecha_revocacion` | `timestamp` | NULL | seteada junto con `revocado = true` |
| `reemplazado_por` | `int8` | NULL | FK autorreferencial a `refresh_token` |
| `motivo_revocacion` | `varchar(20)` | NULL | `'ROTATION'` / `'LOGOUT'` / `'CASCADE'`, null mientras `revocado = false` |
| `fecha_expiracion` | `timestamp` | NOT NULL | |
| `fecha_creacion` | `timestamp` | NOT NULL, default now | |
